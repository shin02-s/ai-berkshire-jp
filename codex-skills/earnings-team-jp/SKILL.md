## Codexアダプター注記

このスキルは `skills/earnings-team-jp.md` から生成され、Claude Code とCodexで正本を共有する。

- `$ARGUMENTS` は現在のCodexタスクにおけるユーザー依頼として扱う。
- ソース中のClaude Code固有インターフェースは機能を落とさず、現在のセッションで最も近いCodex機能へ読み替える。`TeamCreate` は利用可能なサブAgentによるチーム編成、`TaskCreate` は境界の明確な担当割当、`TaskUpdate` は進捗・完了状態の追跡、`SendMessage` はAgent間の追加指示・結果回収、`TeamDelete` と `shutdown_request` は全結果回収後の終了・整理として扱う。
- `Task` / `Agent` は利用可能なサブAgent、`WebSearch` はWeb検索、`Bash` はシェル、`Read` / `Write` は通常のファイル読取・編集へ読み替える。サブAgentを利用できない場合は、同じ役割と検証順序を主タスクで逐次実行し、未実施の並行調査を装わない。
- 共通ツールはリポジトリ直下から実行し、日本版では `--locale ja`、必要に応じて `--market jp` / `--currency JPY` を付ける。
- 調査前に `date` で当日を確認し、データ基準日をレポート冒頭に記載する。
- `AGENTS.md` の品質規則に従い、財務数値の照合、正確な計算、欠損と不確実性を明示する。

# 日本企業の決算精読チーム：4視点並行分析と公開稿作成

## 設計思想

決算短信の増減率を要約するのではなく、事業の質、財務の質、競争環境、リスク・経営説明を独立に読み、相互の盲点を統合する。対象は東証内国普通株に限定し、会社IR、TDnet、EDINETを正本とする。

## フェーズ1：4視点の並行調査

### ステップ1：一次資料を確保する

決算発表日時、対象期間、会計基準、決算期、株価基準日を固定し、次を取得する。

- 決算短信、決算説明資料、補足データ、質疑応答。
- 有価証券報告書または半期報告書、適時開示。
- 前年同期資料、前回会社計画、中期経営計画。
- コーポレートガバナンス報告書、配当・自己株式取得関連資料。

資料が欠ける場合は不足資料と判断への影響を示す。第三者集計を一次資料として扱わない。

### ステップ2：チーム構成を提示する

| Agent | 視点 | 主な責任 |
|---|---|---|
| `business-reader` | 事業の本質 | 数量、単価、構成、顧客、受注、再現性 |
| `financial-auditor` | 財務品質 | 損益、CF、財政状態、株式数、評価 |
| `competition-reader` | 競争環境 | シェア、競合、供給制約、業界先行指標 |
| `risk-reader` | リスク・経営 | 説明の一貫性、ガバナンス、資本配分、赤旗 |

TeamCreateを利用できる場合は `{会社名}-earnings-jp` を作成する。同名チームがある場合は状態を確認し、別企業の作業を混在させない。

### ステップ3：4 Agentを並行起動する

Team・Task機能がある場合は同じメッセージで4 Agentを起動し、TaskCreateで `subject`、`description`、`activeForm` を設定する。利用できない場合は同じ4視点を順番に実行し、各暫定結論を統合前に記録する。

#### Agent 1：事業の本質

1. 売上を数量、単価、製品構成、為替、買収・売却へ分解する。
2. セグメント別利益、受注、稼働率、顧客継続率等のKPIを比較する。
3. 上振れ・下振れが反復可能か、一時要因かを判定する。
4. 会社計画の据置・修正と季節性を確認する。
5. 各項目を改善・横ばい・悪化で表示し、根拠を示す。

#### Agent 2：財務品質

1. 売上高、営業利益、親会社株主帰属利益、EPSを前年同期・計画と比較する。
2. 営業CF、設備投資、FCF、運転資本、在庫、売掛金を点検する。
3. 減損、引当金、税率、非支配持分、連結範囲、一時損益を確認する。
4. 自己株式控除後株式数、希薄化、自己株式取得・消却を確認する。
5. 次のコマンドを実行し、出力を検証記録へ残す。

```bash
python tools/financial_rigor.py --locale ja cross-validate --field {項目} --values '{"決算短信":0,"有価証券報告書":0}' --unit 百万円
python tools/financial_rigor.py --locale ja verify-market-cap --price {株価} --shares {株式数} --reported {時価総額} --currency JPY
python tools/financial_rigor.py --locale ja verify-valuation --price {株価} --eps {EPS} --bvps {BPS} --dividend {配当}
python tools/financial_rigor.py --locale ja three-scenario --price {株価} --eps {EPS} --shares {株式数_億株} --growth {強気} {基準} {弱気} --pe {強気PER} {基準PER} {弱気PER} --currency JPY
```

#### Agent 3：競争環境

1. 同業の直近開示と対象企業の差を確認する。
2. シェア、価格、原材料、納期、在庫、顧客投資の変化を追う。
3. 対象企業の利益変化が会社固有か業界共通かを分ける。
4. 新規参入、代替技術、顧客内製化、規制変更を確認する。
5. 競争優位を強化・不変・弱化で判定する。

#### Agent 4：リスク信号

1. 経営者の語調、説明順、削除された表現、前回からの変化を比較する。
2. 過去の約束と実績を照合し、達成・延期・撤回を記録する。
3. 政策保有株、持合い、親子上場、支配株主、関連当事者取引を確認する。
4. 配当、DOE、自己株式取得、消却、株主優待、増資を評価する。
5. 会計、品質、不祥事、訴訟、サイバー、災害等の赤旗を探す。
6. 経営説明の信頼度を1〜5で採点する。

各Agentは `skills/financial-data-jp.md` に従い、検索不能や資料欠損をteam-leadへ明示する。完了後はTaskUpdateを `completed` にし、SendMessageで完全な報告を送る。

### ステップ4：進捗を追跡する

Agent別の状態を表示し、受領ごとに重要発見3〜5件と未解決事項を示す。4件が揃う前に統合結論を出さない。受領後は `shutdown_request` を送り、終了を確認する。

## フェーズ2：team-leadが統合レポートを作る

### レポート構成

1. 一文結論。
2. 今回最も重要な3つの変化。
3. 4視点の評価表。
4. 主要KPIと前年・計画比較。
5. 事業、財務、競争、リスクの詳細。
6. 利益変動の要因分解と利益の質。
7. 会社計画の達成可能性と季節性。
8. 経営者の語調と約束の追跡。
9. 配当・DOE・自己株式取得等の資本政策。
10. 投資仮説への影響：強化・不変・弱化・破綻。
11. 強気・基準・弱気の三情景と行動条件。
12. 次回までの観測指標。

各視点の意見が割れた場合は平均せず、争点、必要な追加証拠、結論が変わる条件を残す。

## フェーズ3：編集と読者レビュー

統合稿が完成したらTaskCreateで編集と読者レビューの2件を登録し、同じメッセージ内でAgent 5とAgent 6を並行起動する。両者は互いの結論を見ずに作業し、完了時にTaskUpdateとSendMessageで結果をteam-leadへ返す。

### Agent 5：編集

統合レポートを日本語の公開記事へ整える。事実を変えず、重複、曖昧語、過剰な形容、論理の飛躍を除く。重要数値の基準日と単位を残し、元レポートにない結論を加えない。

### Agent 6：読者レビュー

一般の長期投資家として次を確認する。

- 一読で会社、決算の変化、投資上の意味を理解できるか。
- 専門用語や表に説明不足がないか。
- 最大の弱気材料が真剣に扱われているか。
- 未保有者と既存保有者の行動条件が明確か。
- データと推論が区別されているか。

出力は総合評価、良い点、必須修正、任意改善、未回答の質問、一文総評とする。

### team-leadの定稿

編集稿と読者レビューを統合し、修正内容が元データと矛盾しないか再確認する。

## 出力と監査

- 調査版：`reports/{会社名}/{会社名}-earnings-team-{期間}-{YYYYMMDD}.md`
- 公開稿：`reports/{会社名}/{会社名}-earnings-article-{期間}-{YYYYMMDD}.md`

既存ファイルは上書きしない。

```bash
python tools/report_audit.py --locale ja extract --market jp --report {公開稿}
python tools/report_audit.py --locale ja verdict --market jp --results '<照合済みJSON>' --report {公開稿名}
```

監査不合格なら公開稿ではなくドラフトと明記する。これは `earnings-review-jp` の単独精読を置き換えるのではなく、複数視点と編集工程が必要な場合に使う。

全6件の結果と監査状態を確認した後、未処理メッセージがないことを確かめ、各Agentへ `shutdown_request` を送る。終了応答後にTeamDeleteでチーム資源を整理する。失敗したAgentがある場合は、再試行または欠損表示を決める前にチームを削除しない。

## 重要原則

- 発表前予想より、会社計画と過去説明との差を優先する。
- 進捗率だけで通期達成を判断せず、季節性と受注を確認する。
- 株価反応と決算の質を分ける。
- 最新資料を取得できない場合は完了を装わない。
- 4人の投資家本人の発言を捏造しない。
