# WeChat公式アカウント記事：執筆者・編集者・読者の3Agentによる協働

`$ARGUMENTS` を詳細に調査し、そのまま公開できるWeChat公式アカウント向け記事を作成する。3つのAgentが役割を分担する。執筆者は詳細な初稿を書き、編集者は構成と表現を徹底的に整え、読者は対象読者の視点からレビューする。

**対応する入力形式**：テーマの説明。例：`大規模モデルのOPD技術解説`、`Qwen3技術レポートの解説`、`ウォーレン・バフェットがテクノロジー株を買わない理由`

---

## 設計思想

優れたWeChat公式アカウント記事は、3つの観点を同時に満たす必要がある：
1. **深さ**――時間を使って最後まで読む価値がある（執筆者が担当）
2. **読みやすさ**――構成が明確で、リズムが良く、読者を遠ざけない（編集者が担当）
3. **本当に理解できること**――対象読者が途中で読むのを諦めない（読者が担当）

1人での執筆は独りよがりになりやすい。書き手には明確でも、読者には理解できない。3つのAgentが協働する本質は、**外部の視点を強制的に導入すること**にある。

---

## フェーズ1：調査と素材収集

### ステップ1：記事の位置付けを明確にする

執筆開始前に以下を確認する（ユーザーが指定していない場合は積極的に質問する）：

| 観点 | 確認事項 | デフォルト値 |
|------|---------|--------|
| **対象読者** | 技術的な背景の程度 | 多少の技術背景はあるが、当該分野の専門家ではない |
| **記事の深さ** | 入門／中程度の深掘り／専門的 | 中程度の深掘り（数式を含むが、明確に説明） |
| **記事の長さ** | 文字数の範囲 | 3,000～4,000字 |
| **原論文／資料のダウンロードが必要か** | PDF／図版が必要 | はい |
| **文体** | 正式／対話的／鋭い | 対話的（賢い友人に向けて書くように） |

### ステップ2：詳細調査

Agentツールで2～3つの調査Agentを**並列**起動し、十分な素材を収集する：

**調査Agent A：中核内容の調査**
- 論文解説の場合：論文PDFをダウンロードし、中核的な貢献、重要な図表、実験結果を抽出
- 技術テーマの場合：最新動向、重要論文、技術的詳細を検索
- 事業／投資テーマの場合：最新データ、業界レポート、競争環境を検索

**調査Agent B：業界背景と応用**
- 当該技術／テーマの業界での実用化状況を検索
- どの企業が使用しているか？ 効果はどうか？
- 最新の発展傾向と節目となるイベント

**調査Agent C（任意）：競合／比較調査**
- 類似手法／製品との比較
- 歴史的な発展経緯
- 将来の進化方向

### ステップ3：素材の枠組みを整理する

すべての調査Agentの完了後、以下を整理する：
1. **中核的な主張**（記事が伝える中心的な情報を一文で要約）
2. **重要データ**（最も印象的なデータを3～5件）
3. **図版一覧**（必要な図とその出典）
4. **記事構成案**（6～8章のタイトルと中核内容）

## フェーズ2：執筆者Agentが初稿を書く

Agentツールで**執筆者Agent**を起動し、詳細な執筆指示を与える。

### 執筆者AgentのPromptテンプレート

```
あなたは専門的な技術ライター（Author Agent）として、WeChat公式アカウント向けの記事を執筆します。

## 対象読者
{ステップ1で確認した読者像}

## 文体の要件
- 日本語だけで表現し、日本語と英語を不必要に混在させない（技術用語は初出時に英語を示し、その後は日本語を使用）
- 賢い友人に向けた技術解説のように書き、学術論文の翻訳調にしない
- 理解を助ける比喩を使うが、適切でありきたりではないものにする
- 重要な数式／データを含めるが、すべて平易な言葉で説明する
- 絵文字を使わない
- 1段落は4行以内（WeChat公式アカウントの閲覧環境を考慮）

## 中核内容
{整理済みの素材、データ、主張}

## 記事構成の要件
1. **冒頭（最初の3段落）**：強いフックが必須。印象的なデータまたは直感に反する結論で始め、穏やかな比喩から始めない
2. **背景**：なぜ重要か？ どの問題を解決するか？
3. **中核内容（2～3節）**：技術的な深さをここで示すが、各技術項目に「平易な言い換え」を付ける
4. **実証／事例**：データと事例で説明し、抽象論だけにしない
5. **業界への影響／展望**：業界にとって何を意味するか
6. **結び**：画像として切り取って共有できる、拡散力のある一文で締める

## 図版の要件
- 論文解説記事：論文PDFから原図を必ず抽出し、`![説明](相対パス)` で記事へ直接挿入する。[図X：説明] のプレースホルダーを使わない
- 抽出方法：pdftoppmでPDFページを高解像度PNG（900 DPI以上）へレンダリングし、PILで対象図表の領域を切り抜く
- 各画像は500KB以上とし、高解像度を確保
- 画像はすべて `assets/{テーマ略称}/` ディレクトリへ保存
- 論文以外の記事：図版が必要なら適切な画像を検索・ダウンロードし、同様に直接挿入

## 数式の要件
- すべての数式にLaTeX形式を使用：行内は `$...$`、独立した数式は `$$...$$`
- 数式をプレーンテキストで書かない（例：`> D_KL(P || Q) = ...`）。必ずLaTeXでレンダリング可能な形式にする
- 各数式の後に、引き続き「平易な言い換え」を付ける

約{目標文字数}字の完全な記事初稿を書いてください。
```

### 執筆者Agentの完了後

初稿ファイルが生成されたことを確認し、全文を読んで内容の完全性を確認する。

## フェーズ3：編集者Agent + 読者Agentによる並列レビュー

初稿の完成後、Agentツールで編集者Agentと読者Agentを**同一メッセージ内**で起動する。

### 編集者AgentのPromptテンプレート

```
あなたは経験豊富なWeChat公式アカウントの編集者（Editor Agent）です。以下の記事を詳細にレビューし、推敲してください。

## レビュー基準
1. **タイトル**：SNS上でクリックしたくなるか？ 30字を超えて途中で切れないか？
2. **冒頭**：最初の3段落で読者を引き留められるか？ フックは十分強いか？
3. **構成**：投資ロジックの連鎖は滑らかか？ 飛躍や断絶がないか？
4. **深さと読みやすさの両立**：数式／技術部分は本当に平易か？ 「平易なふりをして説明できていない」箇所はないか？
5. **リズム**：長すぎる段落はないか？ 各節の長さは適切か？
6. **図版**：画像が実際に挿入されているか（プレースホルダーではないか）？ 読者が視覚的な補助を最も必要とする位置にあるか？
7. **結び**：拡散力があるか？ 読者は読み終えた後に共有したくなるか？

## 記事全文
{完全な初稿}

## 出力形式
1. 総合評価（3～5文）
2. タイトルの修正案（候補を2～3件）
3. 節ごとの修正案（「原文 → 推奨する修正文」の具体的な対比）
4. 最も重要な改善点3件
```

### 読者AgentのPromptテンプレート

```
あなたは{対象読者像}（Reader Agent）として、読者の視点から以下の記事をレビューします。

## あなたの背景
{対象読者の知識水準と読書習慣の具体的な説明}

## 記事全文
{完全な初稿}

## 次の問いに答えてください
1. 最初の3段落を読んだ後も、読み続けますか？ その理由は？
2. 「理解できない」または「理解するために読み直す必要がある」箇所はどこですか？ 具体的にどの文ですか？
3. 技術／数式部分を理解できましたか？ 「平易な言い換え」は役立ちましたか？
4. 記事の中心的な比喩は適切ですか？ より良い比喩はありますか？
5. 長すぎますか、短すぎますか？ どこで我慢できなくなりますか？
6. 読後、記事の中核的な主張を一文で要約できますか？
7. この記事を共有しますか？ 共有するとき、どのようなコメントを付けますか？
8. 知りたいのに記事で扱われていない問いはありますか？
```

## フェーズ4：最終稿

### ステップ1：2つのAgentからのフィードバックを統合する

以下の頻出問題を重点的に確認する：

| 問題の種類 | 編集者によくある指摘 | 読者によくある指摘 | 対応方法 |
|---------|------------|------------|---------|
| 冒頭が弱い | フックが弱い | 最初の3段落で読み続ける動機がない | データ／直感に反する結論で冒頭を書き直す |
| 技術部分で離脱 | 数式が密集しすぎ | ある段落を3回読み直す必要がある | 数式を削除または画像化し、より直感的な比喩を追加 |
| リズムが冗長 | 特定の節が長すぎる | 特定箇所で我慢できなくなる | 統合または削減（特に後半で繰り返される技術説明） |
| 結びが弱い | 拡散力がない | 共有したくならない | 単独で画像化・共有できる一文へ書き換える |
| 概念の飛躍 | 投資ロジックに断絶がある | 特定箇所で「突然理解できなくなる」 | つなぎの文または背景説明を追加 |

### ステップ2：修正を実行する

フィードバックに基づき記事を書き直す。中核となる修正原則：

1. **編集者と読者の双方が指摘した問題は必ず修正**
2. **編集者だけが指摘した問題も、ほぼ修正する**（編集者の専門的判断は通常正確）
3. **読者だけが指摘した問題は状況に応じて修正**（実際の読書体験を表すが、すべてに対応する必要はない）
4. **両者が矛盾する場合は読者を優先**（編集者は完成度を追求するが、読者体験が最終基準）

### ステップ3：図版を抽出する

論文解説記事は、最終稿の完成前に図版の抽出を完了する：

1. **レンダリング**：`pdftoppm -png -r 900 -f {ページ番号} -l {ページ番号} 論文.pdf /tmp/page`（900 DPIから開始。画像が500KB未満なら1,200または1,500 DPIへ引き上げ）
2. **位置特定**：まず150 DPIで全ページをレンダリングし、各図表のピクセル座標を目視確認
3. **切り抜き**：PILで座標に沿って切り抜き、`compress_level=1` で保存。各画像を500KB以上にする
4. **保存**：`assets/{テーマ略称}/` ディレクトリへ保存し、`fig{番号}-{説明}.png` と命名
5. **挿入**：記事内で `![説明](../../assets/{テーマ略称}/fig{番号}-{説明}.png)` として参照

### ステップ4：最終ファイルを作成する

最終稿をmdファイルとして保存し、ファイル末尾に論文／資料の原文リンクを付ける：

```markdown
**論文原文：**
- arXiv: {リンク}
```

## 執筆上のレッドライン

1. **データを捏造しない**。引用データには必ず情報源を付け、見つからない場合は「推定」と明記
2. **AI調の表現を使わない**。「一緒に見てみましょう」、「注目すべきは」、「言わざるを得ません」などの決まり文句を禁止
3. **過度に約束しない**。技術記事で「破壊的」、「革命的」と言わず、データで説明
4. **数式には平易な説明を付ける**。各数式の後に「平易に言い換えると……」という説明を置く
5. **数式はLaTeXを使用**。`$$...$$` 形式とし、プレーンテキストの数式を禁止
6. **図版を実際に挿入する**。論文解説ではPDFから高解像度の原図（500KB以上）を抽出し、`[図X]` のプレースホルダーを禁止
7. **表の括弧内注記を正確にする**。概念の説明には正確な定義を使い、曖昧な動詞・目的語の表現を使わない（例：「教師由来のテキスト」とし、「教師のテキストを学ぶ」のような曖昧な表現を避ける）
8. **比喩を一貫させる**。全文で1つの中心的な比喩を使い、節ごとに新しい比喩へ変えない
9. **結びに拡散力を持たせる**。最後の一文は、単独で画像化・共有する価値のあるものにする
